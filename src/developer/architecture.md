## 网关的核心价值是什么？ {#gateway-value}

### 面试快答

网关统一入口路由、认证接入、限流、可观测性与部分协议治理。它应保持职责清晰，业务规则和资源级授权仍由业务服务执行。

### 详细解析

网关也是关键依赖，要有容量、故障隔离和回退设计。不要把所有业务聚合、长任务与数据库访问集中到网关，避免形成新的单点瓶颈。

| 能力 | 说明 |
| --- | --- |
| 路由转发 | 按路径、Header、权重将请求分发到对应服务 |
| 认证授权 | 统一校验 Token / 签名，减少各服务重复实现 |
| 限流熔断 | 保护后端不被流量打垮 |
| 协议转换 | HTTP/HTTPS、gRPC/WebSocket 等协议适配 |
| 灰度发布 | 按用户、比例切流到新版本 |
| 日志监控 | 统一 access log、TraceId 注入 |

常见实现：Spring Cloud Gateway、Kong、Nginx + OpenResty、APISIX。

## 网关如何做认证和授权？ {#gateway-auth}

### 面试快答

网关验证身份凭证并传递可信身份上下文，服务端再根据资源和动作做授权。内部身份头要防伪造，跨服务使用受保护的传递通道或签名。

### 详细解析

认证只说明“是谁”，不说明能访问哪个租户和订单。直连服务、重放、Token 撤销及权限变更都要进入设计，不依赖前端隐藏按钮保障安全。

**认证（Authentication）**解决「你是谁」；**授权（Authorization）**解决「你能做什么」。

#### 典型流程

1.  客户端携带 JWT / OAuth2 Access Token / API Key 请求网关。
2.  网关校验签名、过期时间、黑名单，解析出 userId、角色、租户。
3.  网关按路由规则做授权：路径 + HTTP 方法 + 角色/权限码。
4.  通过后转发请求，并将用户信息写入 Header（如 `X-User-Id`）传给下游。

| 方式 | 适用场景 |
| --- | --- |
| JWT 无状态校验 | 网关本地验签，高吞吐 |
| OAuth2 Introspection | 需实时吊销、强管控 |
| API Key + HMAC 签名 | 开放 API、B2B 对接 |

**注意：**网关是第一道防线，但业务服务仍需做关键权限校验（纵深防御），不能完全信任 Header。

## 限流、熔断、降级分别解决什么问题？ {#rate-limit-circuit-degrade}

### 面试快答

限流控制进入系统的负载，熔断在依赖持续失败时快速拒绝，降级用较低能力维持关键服务。三者需配合超时、隔离和恢复探测。

### 详细解析

熔断半开阶段用少量探测请求判断恢复，不能一次放开全部流量。降级结果需保留业务语义，不能把“没有查到”与“服务暂不可用”返回成相同成功结果。

| 机制 | 触发方 | 目标 | 典型手段 |
| --- | --- | --- | --- |
| 限流 | 入口 / 调用方 | 控制流量上限，防止过载 | 令牌桶、漏桶、滑动窗口 |
| 熔断 | 调用方 | 下游故障时快速失败，避免线程/连接被拖死 | Sentinel、Hystrix、Resilience4j |
| 降级 | 被调方 / 调用方 | 高压或故障时关闭非核心能力，保核心链路 | 返回默认值、读缓存、关闭推荐模块 |

```bash
正常：请求 -> 限流通过 -> 调用下游 -> 返回
熔断：下游错误率超阈值 -> 熔断打开 -> 直接返回 fallback
降级：库存服务超时 -> 跳过推荐位 -> 仅展示核心商品信息
```

组合使用：限流防突发、熔断防故障扩散、降级保核心业务可用。

## MQ 如何实现削峰填谷？ {#mq-peak-shaving}

### 面试快答

MQ 把瞬时写入流量转成可控的异步处理速率，以队列空间和处理延迟换取下游平稳。前提是业务接受异步结果，并且长期平均消费能力足够。

### 详细解析

队列不是无限缓冲，要定义积压上限、过期、优先级和拒绝策略。生产长期高于消费时必须扩容或限流，不能靠继续堆积解决。

```bash
秒杀场景：
用户请求 -> 网关限流 -> 写入 MQ（毫秒级返回"排队中"）
         -> 消费者按 500 QPS 扣库存、创建订单
```

#### 收益与代价

| 收益 | 代价 / 需处理 |
| --- | --- |
| 保护 DB / 下游服务 | 链路变异步，用户体验需轮询或推送 |
| 平滑资源使用 | 消息可靠性（ACK、重试、死信） |
| 可水平扩展消费者 | 重复消费需幂等、积压需监控告警 |

## 接口幂等性为什么重要？ {#idempotency}

### 面试快答

幂等保证同一业务操作重复请求不会产生额外副作用，通常用稳定业务键、唯一约束和状态机实现。去重记录要与业务结果原子提交。

### 详细解析

设计请求键的作用域、有效期、参数一致性和并发处理状态。重复请求应返回已知结果或处理中状态，不要仅凭短 TTL 锁认定永久幂等。

#### 不幂等的后果

-   重复扣款、重复下单、重复发券。
-   库存被多次扣减。

#### 常见实现

| 方案 | 原理 |
| --- | --- |
| 唯一请求号 + 去重表 | 先 INSERT 请求号，唯一索引冲突则拒绝 |
| 数据库唯一索引 | 订单号、业务流水号天然防重 |
| 状态机 | 只允许特定状态流转，重复请求无效 |
| Token 机制 | 提交前先获取一次性 Token |
| 分布式锁 | 同一资源同一时刻只处理一次 |

```bash
INSERT INTO idempotent (request_id, status)
VALUES ('req-001', 'processing');
-- 重复请求触发唯一索引冲突，直接返回上次结果
```

## 高并发下单接口如何设计？ {#high-concurrency-order}

### 面试快答

先明确库存、支付和订单状态的不变量，再用限流、原子库存约束、幂等与可靠异步流程保护链路。缓存可减压，数据库或权威存储负责最终一致性约束。

### 详细解析

扣库存需防超卖和重复扣减，订单超时与支付回调应由状态机协调。准备超时未知、消息重复、补偿失败与热点分区等故障场景，并通过压测和对账验证。

#### 分层设计

1.  **前端：**按钮防重复点击、验证码/答题。
2.  **网关：**全局限流 + 用户级限流。
3.  **应用：**Token 防重、参数校验、异步化非核心步骤。
4.  **库存：**Redis 预扣（Lua 原子）或 DB 乐观扣减 `WHERE stock > 0`。
5.  **订单：**唯一索引 + 状态机 + MQ 异步落库/通知。

```bash
UPDATE product SET stock = stock - 1
WHERE id = ? AND stock > 0;
-- affected_rows = 0 表示库存不足
```

补偿机制：MQ 消费失败重试、超时关单、对账任务兜底。

## 重试机制有哪些风险？ {#retry-risks}

### 面试快答

重试可能放大流量、延长尾延迟并重复执行副作用。仅对可恢复且安全重试的失败设置有限次数、退避和抖动，避免多层同时重试。

### 详细解析

整体截止时间优先于每层独立超时。写操作超时后结果可能未知，使用幂等键和结果查询，不能将网络超时自动解释为业务未执行。

-   **重试风暴：**大量客户端同时重试，流量成倍放大，压垮已脆弱的下游。
-   **重复写入：**请求实际已成功但响应超时，重试导致重复操作。
-   **延迟堆积：**重试占用线程/连接，拖慢整体吞吐。
-   **故障扩大：**短暂抖动被重试放大成长期不可用。

#### 安全重试原则

| 原则 | 说明 |
| --- | --- |
| 只重试幂等操作 | 写操作必须有幂等键 |
| 指数退避 + 抖动 | 1s → 2s → 4s + random |
| 限制最大次数 | 通常 2~3 次 |
| 配合熔断 | 下游已熔断则不再重试 |
| 区分错误类型 | 4xx 不重试，5xx/超时可选重试 |

## CAP 理论是什么？ {#cap-theory}

### 面试快答

在网络分区下，分布式系统无法同时保证 CAP 意义上的一致性和可用性。讨论必须说明分区、操作和一致性模型，不能把它当成日常“随便三选二”。

### 详细解析

CAP 的一致性通常指线性一致性，可用性也有严格定义。实际设计还需讨论延迟、恢复、耐久性与业务可接受的陈旧窗口，避免只贴 CP/AP 标签。

-   **C（Consistency）：**所有节点同一时刻看到相同数据。
-   **A（Availability）：**每个请求都能得到响应（不保证最新）。
-   **P（Partition tolerance）：**网络分区发生时系统仍能运行。

分布式系统网络分区不可避免，因此实际是在 **CP** 与 **AP** 之间取舍：

| 类型 | 代表 | 特点 |
| --- | --- | --- |
| CP | ZooKeeper、Etcd | 强一致，分区时可能拒绝服务 |
| AP | Eureka、Cassandra | 高可用，允许短暂不一致 |

CAP 是理论模型，工程上更关注延迟、吞吐和业务可接受的不一致窗口。

## 负载均衡有哪些常见算法？ {#load-balance-algorithms}

### 面试快答

轮询、加权、最少连接、一致性哈希等算法适合不同负载。策略应考虑请求耗时差异、实例能力、健康状态和会话约束，并在故障时及时摘除节点。

### 详细解析

客户端、网关和服务发现都可能参与选择，避免多层策略叠加失真。一致性哈希降低节点变化时的迁移，但不能自动解决热点 key 或容量不均。

| 算法 | 原理 | 适用 |
| --- | --- | --- |
| 轮询（Round Robin） | 依次分配 | 实例同构、无状态 |
| 加权轮询 | 按权重比例分配 | 机器配置不同 |
| 随机 | 随机选实例 | 简单场景 |
| 最少连接 | 选连接数最少的 | 长连接、耗时差异大 |
| 一致性哈希 | hash(key) 映射环 | 有状态、缓存 |
| 源地址哈希 | 同一客户端固定到同一节点 | 会话保持 |

## 服务限流有哪些算法？ {#rate-limit-algorithms}

### 面试快答

固定窗口简单但有边界突发，滑动窗口更平滑，漏桶偏向匀速输出，令牌桶允许受控突发。选择要对应业务指标、分布式精度与实现成本。

### 详细解析

按用户、租户、接口或资源分别设限，必要时增加并发上限。明确超限返回、重试提示与限流存储故障策略，避免所有调用方同时重试。

| 算法 | 原理 | 特点 |
| --- | --- | --- |
| 固定窗口 | 每窗口计数，超限拒绝 | 简单，边界可能突刺 2 倍 |
| 滑动窗口 | 细粒度窗口滑动统计 | 更平滑 |
| 令牌桶 | 匀速放令牌，有令牌才通过 | 允许一定突发 |
| 漏桶 | 请求进桶，恒定速率流出 | 输出严格平滑 |

网关常用令牌桶；Redis + Lua 可实现分布式滑动窗口/令牌桶。

## 超时设置应该遵循什么原则？ {#timeout-principles}

### 面试快答

超时应从端到端延迟预算倒推，覆盖连接、排队、执行和重试。依赖调用要使用剩余截止时间，而不是每层都重新获得完整超时额度。

### 详细解析

取消等待不一定终止远端操作，外部写入要有结果确认机制。用实际延迟分布和业务 SLO 定义超时，避免只根据平均值设置。

-   **端到端预算：**总超时 = 各 hop 超时之和 + 余量，上游超时 > 下游超时。
-   **区分读写：**读可短（100~500ms），写/复杂查询可长。
-   **避免过长：**超时过长占满线程池；过短误杀正常慢请求。
-   **可配置：**按接口 SLA 动态调整，支持熔断联动。
-   **传递 deadline：**gRPC deadline、HTTP Header 传递剩余时间。

```bash
Gateway 3000ms > Order 2000ms > Inventory 1000ms > DB 500ms
```

## 服务注册与发现的原理是什么？ {#service-discovery}

### 面试快答

服务实例注册地址和健康信息，调用方或代理通过发现机制得到可用后端。设计需处理注册延迟、缓存、心跳失效、地址变化和优雅下线。

### 详细解析

发现中心短暂不可用时常依赖本地缓存继续服务，但要防陈旧节点。健康检查不等于业务完全健康，结合被动失败、摘流和恢复探测降低错误路由。

1.  **注册：**服务启动向 Registry 写入实例信息（IP、端口、元数据）。
2.  **心跳：**定时续约，超时未心跳则剔除（临时节点）。
3.  **发现：**Consumer 订阅服务名，获取实例列表。
4.  **推送/拉取：**Registry 变更通知 Consumer 更新本地缓存。
5.  **调用：**Client LB 选实例发起 RPC。

代表：Nacos、Eureka、Consul、ZooKeeper。K8s 内置 Service + DNS 也是一种发现机制。
