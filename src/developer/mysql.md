## MySQL 四种隔离级别 {#isolation}

### 面试快答

InnoDB 常见隔离级别为读未提交、读已提交、可重复读和串行化，默认通常是可重复读。隔离效果由快照读、锁定读和锁范围共同决定，不能只背异常对照表。

### 详细解析

读已提交通常每次一致性读创建新快照，可重复读通常沿用首次一致性读的快照。锁定读读取较新状态并加锁，混用时要解释清楚实际看到的数据。

#### 四种隔离级别

| 级别 | 理解重点 |
| --- | --- |
| READ UNCOMMITTED | 可能读到其他事务未提交的数据，通常不用于常规业务 |
| READ COMMITTED | 一致性读通常每条语句取新快照，可能看到后续提交 |
| REPEATABLE READ | 同事务的一致性读通常沿用首次一致性读的快照 |
| SERIALIZABLE | 使用更强的并发控制，代价可能是更多阻塞与重试 |

#### 快照与锁共同理解

InnoDB 默认一般为 REPEATABLE READ，但应查实际配置。快照读的视角与锁定读不同：SELECT ... FOR UPDATE 或写操作需要读取与锁定相关记录，不能认为整个事务的所有语句永远看到同一旧状态。

RR 的一致性读通过快照保持结果视角，特定锁定范围通过 Next-Key Lock 限制插入。不要用一句“RR 完全没有幻读”替代对 SQL、索引和交错执行的说明。

#### 选型

按业务不变量设计唯一约束、条件更新和事务边界；隔离级别本身不能替代幂等和并发控制。通过两个会话复现实例验证锁与可见性。

#### 参考资料

[InnoDB 一致性读](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)（2026-10-18 核验，注意目标部署版本。）

## select for update 使用场景 {#for-update}

### 面试快答

SELECT ... FOR UPDATE 在事务内读取并锁定目标记录，用于后续依赖该状态的更新。应保证走合适索引、事务足够短，并用条件更新或约束守住业务不变量。

### 详细解析

锁的是扫描涉及的索引记录及可能的间隙，不是语义上“只锁结果那一行”。自动提交、访问路径和隔离级别都会影响实际锁行为。

`SELECT ... FOR UPDATE` 用于在事务中查询数据并对查询到的行加**排他锁（X 锁）**，阻止其他事务同时修改这些行。普通读可以读，当前读(for update)和写会等(update delete)。

```sql
BEGIN;

SELECT * FROM account WHERE id = 1 FOR UPDATE;
// 判断余额足够
UPDATE account SET balance = balance - 100 WHERE id = 1;

COMMIT;
```

#### 适用场景

-   扣库存、扣余额、订单状态流转。
-   抢券、分布式任务领取、防止并发重复处理。

```sql
BEGIN;

SELECT stock FROM product WHERE id = 100 FOR UPDATE;

UPDATE product
SET stock = stock - 1
WHERE id = 100 AND stock > 0;

COMMIT;
```

#### 注意点

1.  必须在事务中使用，否则锁会立即释放。
2.  查询条件最好命中索引，否则可能锁表或锁范围扩大。
3.  只对 InnoDB 等支持事务和行锁的引擎有效。
4.  避免长事务，锁持有时间越长，越容易造成阻塞甚至死锁。

`FOR UPDATE` 属于**当前读**，会读取最新版本并加锁，与普通快照读行为不同。

## MySQL 索引为什么能加快查询？ {#index-speed}

### 面试快答

B+Tree 索引通过有序查找减少需要访问的数据页，并支持范围遍历。索引包含维护和存储成本，应让访问路径匹配筛选、排序和覆盖需求。

### 详细解析

索引不保证每次都更快，小表、低选择性或大量回表时全表扫描可能更便宜。B+Tree 的高扇出和叶子链表适合页式存储与范围查询，而非简单宣称树越矮越快。

#### 核心原理

| 机制 | 说明 |
| --- | --- |
| 有序结构 | B+Tree 叶子节点按索引列有序，**支持等值和范围查找** |
| 减少 IO | 树高通常 **3～4 层**，百万级数据只需几次磁盘页读取 |
| 缩小扫描范围 | 从 **O(n)** 全表扫描降为 **O(log n)** 索引定位 |

```text
无索引：逐行扫描整张表
有索引：根节点 -> 中间节点 -> 叶子节点 -> 命中目标行
```

索引不是越多越好。索引会占用磁盘空间，并增加插入、更新、删除时维护 B+Tree 的成本；写多读少的表应谨慎建索引。

## 聚簇索引和非聚簇索引区别？ {#clustered-index}

### 面试快答

InnoDB 聚簇索引的叶子存放整行数据，二级索引叶子通常带主键值。二级索引查到主键后再查聚簇索引叫回表，覆盖查询可减少这一步。

### 详细解析

主键过宽会放大每棵二级索引的体积；随机主键也可能增加页分裂。设计主键时结合写入模式、分布式 ID 和安全需求，而非一律要求自增。

**聚簇索引**的叶子节点保存整行数据；

**非聚簇索引（二级索引）**的叶子节点保存索引列值和对应的主键值。

#### 对比

| 类型 | 叶子节点内容 | 数量 |
| --- | --- | --- |
| 聚簇索引 | 整行数据 | 每张表只有一个（通常是主键） |
| 二级索引 | 索引列 + 主键值 | 可建多个 |

#### 回表

通过二级索引查到主键后，再回到聚簇索引查整行数据，这个过程叫**回表**。回表次数越多，查询越慢。

```sql
-- 二级索引 idx_name 查到 id=100
-- 再回聚簇索引查 id=100 的整行
SELECT * FROM user WHERE name = 'Tom';
```

覆盖索引可以避免回表；没有主键时 InnoDB 会选唯一非空索引，否则自动生成 hidden row\_id 作为聚簇索引。

## 覆盖索引是什么？ {#covering-index}

### 面试快答

覆盖索引指查询所需列能从一个索引中取得，通常可减少回表。应结合过滤条件、返回列和执行计划确认，不为覆盖而无限追加宽字段。

### 详细解析

更新频繁或长字符串列会放大写放大和缓存压力。Extra 的 Using index、Using index condition 含义不同，后者不表示一定无需回表。

Extra 中通常出现 `Using index`。`Extra` 是 `EXPLAIN` 执行计划里的一个字段

（`EXPLAIN` 执行计：划查看 SQL 大概会怎么执行、用不用索引、扫描多少行、是否回表、排序、临时表）

```sql
CREATE INDEX idx_user_name_age ON user(name, age);

SELECT name, age
FROM user
WHERE name = 'Tom';
```

这个查询只需要 `name` 和 `age`，联合索引已包含全部列，可直接从索引返回结果。

#### 收益与注意

| 收益 | 注意 |
| --- | --- |
| 减少回表 IO | 索引列不宜过多，否则写入成本上升 |
| 减少随机 IO | `SELECT *` 很难形成覆盖索引 |
| 优化 COUNT、分页等 | 需结合最左前缀设计联合索引 |

## 最左前缀原则是什么？ {#left-prefix}

### 面试快答

复合索引按列的字典序组织，通常从最左列及其连续前缀有效定位。等值、范围、排序和具体优化策略共同决定哪些列参与定位或过滤。

### 详细解析

不要背成“遇到范围后所有列完全无效”，后续列可能参与条件过滤、覆盖或排序，具体看执行计划。设计时从真实 SQL 和数据分布出发。

#### 有序索引的含义

索引 (a,b,c) 按 a 优先、再 b、再 c 排列。a 与 b 的等值条件通常能形成较精确定位，只给 b、c 时往往不能同样高效地定位，但仍可能因为覆盖、扫描或特定优化器策略使用该索引。

#### 范围条件的边界

范围查询后面的列是否用于边界、过滤、排序或覆盖，取决于操作符、索引及优化器。不能把“范围之后全部失效”当普遍定律，应检查 key、key_len、rows、Extra 以及实际扫描量。

#### 设计方法

从高频 SQL、等值与范围条件、排序和返回列一起设计；考虑不同查询是否能复用索引。使用真实数据分布对比计划与执行延迟，不为单条 SQL 添加过多重复索引。

## MVCC 是什么？ {#mvcc}

### 面试快答

MVCC 借助版本信息、Undo 和 Read View 为一致性读选择可见版本，减少读写互相阻塞。它不等于所有操作都无锁，锁定读和写入仍依赖锁。

### 详细解析

可重复读中的快照主要解决一致性读视角问题；更新、锁定读与快照混用可能看到不同状态。长事务会拖延旧版本清理，应监控事务年龄与历史链长度。

#### InnoDB 实现要点

| 组件 | 作用 |
| --- | --- |
| 隐藏列 DB\_TRX\_ID | 记录最后修改该行的事务 ID |
| 隐藏列 DB\_ROLL\_PTR | 指向 undo log 中的旧版本 |
| undo log 版本链 | 串联同一行的多个历史版本 |
| Read View | 决定当前事务能看到哪些版本 |

```text
快照读：普通 SELECT，读 Read View 可见的历史版本，不加锁
当前读：SELECT FOR UPDATE / UPDATE / DELETE，读最新版本并可能加锁
```

RC 级别每次 SELECT 生成新 Read View；RR 级别事务首次 SELECT 生成 Read View 并复用，因此 RR 下同一事务多次读结果一致。

#### 参考资料

[InnoDB 一致性读](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)（2026-10-18 核验，注意目标部署版本。）

## MySQL 慢查询怎么排查？ {#slow-query}

### 面试快答

慢 SQL 先确认耗时发生在等待连接、等待锁、执行还是结果传输，再结合慢日志、执行计划和真实数据分布定位。优化应验证扫描行数、索引、返回量和端到端延迟。

### 详细解析

关注 EXPLAIN 的访问方式、key、rows、filtered 与 Extra，必要时用受控的 EXPLAIN ANALYZE 查看实际执行。它会真正执行查询，生产环境要评估开销。

#### 排查步骤

1.  开启慢查询日志，找出耗时 SQL。
2.  使用 `EXPLAIN` 查看访问类型、索引、扫描行数。
3.  检查是否全表扫描、索引失效、回表过多、排序/临时表过大。
4.  优化索引、改写 SQL、减少返回列、优化分页。
5.  结合业务判断是否需要缓存、读写分离或归档历史数据。

```sql
-- 开启慢查询（示例）
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;

EXPLAIN SELECT id, name FROM user WHERE status = 1;
```

#### 重点观察字段

| 字段 | 关注点 |
| --- | --- |
| `type` | 访问方式，尽量避免 `ALL` 全表扫描 |
| `key` | 实际使用的索引 |
| `rows` | 优化器估算扫描行数 |
| `Extra` | 是否出现 filesort、temporary、Using index |

## Next-Key Lock 是什么？ {#next-key-lock}

### 面试快答

Next-Key Lock 组合记录锁和记录前间隙锁，InnoDB 在特定隔离级别与访问路径下用它限制范围内并发插入。锁范围由索引扫描决定。

### 详细解析

唯一索引的唯一值等值查询可能退化为记录锁，范围扫描则不同。排查锁冲突时必须拿到索引、SQL、参数、隔离级别和事务先后顺序。

锁住索引记录及其前面的间隙，用于避免并发插入导致的幻读。

#### 三种锁

| 锁类型 | 锁住范围 |
| --- | --- |
| Record Lock | 单条索引记录 |
| Gap Lock | 两条索引记录之间的间隙（不含记录本身） |
| Next-Key Lock | 记录 + 该记录前的间隙 |

```sql
-- 假设 id 索引有 10、20、30
SELECT * FROM t WHERE id = 20 FOR UPDATE;
-- 可能锁住 (10, 20] 区间，阻止 id=15 的插入
```

**Next-Key Lock 依赖索引**。若查询未命中索引，可能退化为锁大量记录甚至锁表，严重影响并发。RC 级别通常不使用 Gap Lock。

## MySQL Server 层与存储引擎如何分工？ {#mysql-layer-and-logs}

### 面试快答

MySQL Server 负责连接、解析、优化和执行协调，存储引擎负责数据访问与事务细节。Redo 支撑崩溃恢复，Undo 支撑回滚和版本读取，Binlog 支撑复制及恢复链路。

### 详细解析

Redo 与 Binlog 协调提交以减少两者状态不一致的风险。参数配置、刷盘、复制确认和故障模型共同决定数据耐久性，不能用“有日志所以绝不丢”概括。

#### 1\. Server 层 vs 存储引擎层

MySQL 采用**插件式存储引擎架构**：Server 层负责 SQL 处理与通用能力，存储引擎层负责数据的物理组织与读写。

| 层级 | 职责 |
| --- | --- |
| **Server 层** | 连接器、解析器、优化器、执行器；存储过程/视图/触发器/权限；**binlog**；与客户端通信 |
| **存储引擎层** | InnoDB：B+Tree、Buffer Pool、**redo/undo log**、行锁、MVCC；MyISAM/Memory 等 |

```sql
客户端
-> Server 层（解析、优化、执行器）
-> 存储引擎层（InnoDB 读写数据页）
```

执行器通过统一接口调用引擎，因此同一套 Server 可对接不同存储引擎；生产环境几乎都用 InnoDB。

#### 2\. 三种日志分别做什么

| 日志 | 所在层 | 作用 | 特点 |
| --- | --- | --- | --- |
| **binlog** | Server 层 | 归档日志，**主从复制、基于时间点恢复** | 逻辑日志，追加写 |
| **redo log** | InnoDB | 重做日志，保证**事务持久性**，崩溃后恢复已提交修改 | 物理/物理逻辑日志，循环写（WAL） |
| **undo log** | InnoDB | 回滚日志，**事务回滚** + MVCC 多版本可见性 | 保存旧值，purge 线程异步清理 |

```sql
更新一行数据的日志协作：
1. 写 undo log（保存旧值，供回滚和 MVCC）
2. 更新 Buffer Pool 中的数据页
3. 写 redo log
4. 写 binlog
5. redo log commit（两阶段提交）
```

**WAL 原则（Write-Ahead Logging）：**先写日志，再写数据页。崩溃后通过 redo 重做、undo 撤销。

#### 3\. redo 与 binlog 的两阶段提交（2PC）

redo log 属于 InnoDB 引擎层，binlog 属于 Server 层，两者分属不同模块。若只写其中一个就 crash，会导致**主库数据与 binlog 不一致**，从库回放 binlog 时丢事务或重复。两阶段提交保证二者逻辑一致。

```sql
1. Prepare：InnoDB 写 redo log，状态标记为 prepare
2. 写 binlog 到磁盘
3. Commit：InnoDB 将 redo log 标记为 commit
```

#### 4\. 崩溃恢复如何判断

| 崩溃时机 | 恢复行为 |
| --- | --- |
| redo prepare 后、binlog 写完前 | 无 binlog 对应记录，事务**回滚** |
| binlog 写完、redo commit 前 | binlog 已有记录（通过 XID 关联），事务**提交** |
| redo commit 后 | 事务已完整提交，redo 重做保障数据页恢复 |

MySQL 启动时 InnoDB 自动执行 crash recovery：扫描 redo log → 对比 binlog XID → 应提交的用 redo 重做 → 应回滚的用 undo 撤销。

#### 5\. 可靠性配置

-   `innodb_flush_log_at_trx_commit=1`：每次事务 redo log 刷盘，持久性最高。
-   `sync_binlog=1`：每次事务 binlog 刷盘，主从一致最可靠。
-   设为 2 或 0 可换性能，但 crash 可能丢失最近 1 秒事务。

## MySQL 自增主键一定连续吗？ {#auto-increment-gap}

### 面试快答

自增主键提供唯一分配机制，不保证连续或无空洞。事务回滚、失败写入、批量预分配等都可能产生间隙，因此不能把它当业务连续编号。

### 详细解析

财务流水等连续编号应按独立业务规则设计，并考虑并发与审计。主键出现空洞不直接说明丢数据，要对照提交记录和业务事件。

**不一定。** `AUTO_INCREMENT` 保证递增趋势，但不保证严格连续、无空洞。

#### 出现间隙的常见原因

-   事务回滚：已分配的自增值不会回收。
-   批量插入：InnoDB 可能一次预分配多个 id 以提升性能。
-   手动指定 id 或 `INSERT ... ON DUPLICATE KEY UPDATE`。
-   主从切换、重启后 `auto_increment_offset` 等配置影响。
-   删除数据后 id 不会复用。

```sql
BEGIN;
INSERT INTO t VALUES (NULL, 'a');  -- 假设分配到 id=10
ROLLBACK;
INSERT INTO t VALUES (NULL, 'b');  -- 下一条可能是 id=11，10 不会被复用
```

自增主键的价值在于**单调递增、插入性能好、B+Tree 页分裂少**，而不是业务编号连续性。需要连续业务号应单独设计发号器或序列表。

## 深分页为什么慢？如何优化？ {#deep-pagination}

### 面试快答

大 OFFSET 往往需要扫描并跳过大量记录，页数越深成本越高。优先用稳定排序字段加唯一键的游标分页，必要时先查窄索引再关联取详情。

### 详细解析

游标应包含完整排序条件，处理相同时间戳与并发新增。随机跳页需求与顺序翻页不同，需要在产品体验、快照一致性和查询成本间取舍。

`LIMIT offset, size` 中 offset 很大时，MySQL 仍需扫描并丢弃前 offset 行，成本随页码线性增长。

#### 慢的原因

-   `LIMIT 1000000, 20` 需先读 1000020 行再丢弃前 1000000 行。
-   若有 ORDER BY 且无法走索引，还会触发 filesort。

#### 优化方案

| 方案 | 适用场景 |
| --- | --- |
| 游标/Seek 分页 | `WHERE id > last_id LIMIT 20`，无限滚动 |
| 延迟关联 | 子查询先查 id，再 JOIN 取全列 |
| 覆盖索引 | 排序列在索引中，减少回表 |
| 搜索引擎 | 复杂筛选排序交给 ES 等 |

```sql
-- 游标分页（推荐）
SELECT * FROM orders
WHERE id > 1000000
ORDER BY id
LIMIT 20;
```

## 数据冷热分离是什么？ {#hot-cold-separation}

### 面试快答

冷热分离按访问频率或生命周期把数据放到不同存储和索引层，降低在线数据规模。先定义业务查询窗口、归档条件和恢复要求，再设计迁移。

### 详细解析

归档要校验数量与内容，控制分批写入和复制压力，并保留可回查路径。分区、分表与对象存储各有约束，不能因为数据老就直接删除。

#### 常见做法

| 方式 | 说明 |
| --- | --- |
| 分表归档 | 按时间将历史订单迁到 archive 表或历史库 |
| 不同存储介质 | 热数据 SSD，冷数据 HDD 或对象存储 |
| 只读从库 | 历史查询走从库或 OLAP 引擎 |
| TTL + 清理 | 日志类数据定期删除或压缩 |

```sql
orders_2024  -- 热表，SSD，主库
orders_2023  -- 温表，从库可查
orders_hist  -- 冷数据，归档到对象存储 / ClickHouse
```

设计时需考虑：跨冷热数据查询如何路由、归档任务一致性、回查冷数据的延迟 acceptable 范围。

## 读写分离会带来什么问题？ {#read-write-split}

### 面试快答

读写分离把部分读流量放到副本，主要风险是复制延迟导致读到旧数据。写后读可走主库、按复制进度等待或在业务上接受有界延迟。

### 详细解析

先区分网络、主库大事务、应用速度和资源竞争造成的延迟。所有请求都强制读主会失去扩展收益，按一致性需求路由更合理。

#### 典型问题

| 问题 | 场景 |
| --- | --- |
| 主从延迟 | 刚注册完读从库，查不到刚写入的数据 |
| 读己之写 | 用户改密码后立即登录，从库还是旧密码 |
| 路由复杂度 | 需中间件或框架决定走主还是从 |
| 从库故障 | 读流量需 failover，可能全部压到主库 |

#### 常见应对

-   写后读主：关键操作后强制走主库。
-   延迟检测：从库延迟超阈值时读主。
-   会话粘滞：同一用户短时间走同一从库（不能根本解决延迟）。
-   缓存：写时更新缓存，读优先走缓存。

## 索引下推是什么？ {#index-condition-pushdown}

### 面试快答

索引条件下推让存储引擎先用索引里的字段过滤，减少不必要的整行读取。它改善二级索引扫描的回表成本，但不能代替合适的索引列顺序。

### 详细解析

观察 Using index condition 时仍要看扫描量和返回量。优化效果取决于谓词能否下推、选择性以及是否原本就覆盖查询。

```sql
CREATE INDEX idx_name_age ON user(name, age);

SELECT * FROM user WHERE name LIKE '张%' AND age = 25;
```

#### 无 ICP

Server 层用 `name LIKE '张%'` 在索引定位，回表取整行后再在 Server 层过滤 `age = 25`。

#### 有 ICP

引擎层在索引遍历时同时判断 `age = 25`（若 age 在索引中），不满足则不回表。Extra 显示 `Using index condition`。

ICP 适用于：联合索引中，前导列范围匹配，后续列仍可在引擎层过滤的场景。

## 索引失效的常见场景有哪些？ {#index-failure}

### 面试快答

所谓“索引失效”可能是无法有效定位，也可能是优化器认为扫描更便宜。函数或类型转换、前导通配符、低选择性和条件组合都要结合索引及计划判断。

### 详细解析

不要宣称所有 OR、!= 或范围查询必然不走索引。先检查列类型、隐式转换、统计信息和成本估算，再通过改写或索引设计验证收益。

| 场景 | 示例 |
| --- | --- |
| 违反最左前缀 | 联合索引 (a,b,c)，条件只有 b、c |
| 对列做函数/运算 | `WHERE YEAR(create_time) = 2024` |
| 隐式类型转换 | 字符串列与数字比较 |
| 前导模糊匹配 | `LIKE '%abc'` |
| OR 连接不同列 | `WHERE a=1 OR b=2` 可能全表扫 |
| 不等于 / NOT IN | 优化器可能认为全表扫更优 |

```sql
-- 失效
WHERE DATE(create_time) = '2024-06-01'

-- 改写为范围，可走索引
WHERE create_time >= '2024-06-01' AND create_time < '2024-06-02'
```

是否走索引以 `EXPLAIN` 为准，规则是经验法则，优化器还会结合统计信息做 cost 估算。

## MySQL 主从复制原理是什么？ {#replication-principle}

### 面试快答

主库将变更记录到 Binlog，副本接收并应用日志以维护副本数据。异步、半同步等机制的确认边界不同，读到数据的时间也不同。

### 详细解析

复制不等于备份，误删除也会传播；还需快照与日志恢复链路。故障切换要确认副本追赶状态、旧主隔离和客户端路由，避免双写。

```text
主库：事务提交 -> 写 binlog
从库 IO 线程：连接主库 -> 拉取 binlog -> 写入 relay log
从库 SQL 线程：读取 relay log -> 重放 SQL/行事件 -> 更新本地数据
```

#### 复制格式

| 格式 | 说明 |
| --- | --- |
| STATEMENT | 记录 SQL 语句，日志小但可能不一致（如 UUID()） |
| ROW | 记录行变更，可靠，日志较大，生产推荐 |
| MIXED | 混合模式，由 Server 自动选择 |

现代架构常用 GTID 复制，便于 failover 和主从切换；读写分离、备份、高可用都依赖复制链路稳定。

## MySQL 如何保证崩溃恢复？ {#crash-recovery}

### 面试快答

InnoDB 用 Redo 重放必要修改，并结合 Undo 处理未提交事务，以恢复事务一致性。持久化强度还取决于刷盘设置、文件系统和存储故障。

### 详细解析

讨论丢失窗口时明确 innodb_flush_log_at_trx_commit、sync_binlog 和复制配置。定期做恢复演练，验证备份可用及实际 RPO/RTO，而非只检查文件存在。

#### 恢复流程

1.  扫描 redo log，找出已 prepare 或 commit 的事务。
2.  对比 binlog 的 XID，判断事务是否应提交。
3.  应提交的：用 redo 重做已提交修改。
4.  应回滚的：用 undo log 回滚未提交事务。

```sql
WAL 原则（Write-Ahead Logging）：
先写日志，再写数据页
崩溃后通过 redo 重做，通过 undo 撤销
```

`innodb_flush_log_at_trx_commit=1` 与 `sync_binlog=1` 配合可保证每次事务提交都刷盘，可靠性最高；设为 2 或 0 可换性能但 crash 可能丢最近事务。

## 分库分表：如何拆分？ {#sharding}

### 面试快答

分库分表前先确认单库瓶颈与常规优化上限，再选择稳定且分布均衡的分片键。拆分会增加跨片查询、事务、扩容、全局唯一 ID 和运维成本。

### 详细解析

用真实热点与数据增长评估路由和再分片，跨片分页不能简单拼各片 OFFSET。迁移需做增量同步、数据校验、灰度路由与回滚方案。

#### 1\. 适合什么场景

| 信号 | 说明 |
| --- | --- |
| 单表过大 | 行数亿级、B+Tree 深度增加、DDL 耗时小时级 |
| 写入瓶颈 | 单主库 TPS 到顶，垂直扩容无效 |
| 存储瓶颈 | 磁盘/备份/恢复窗口不可接受 |
| 热点集中 | 单行/单分片过热，需打散 |

**不适合：**数据量小、QPS 低（索引优化 + 读写分离即可）；复杂跨分片 JOIN/事务多；团队缺乏分片治理经验。

演进顺序：SQL/索引优化 → 缓存 → 读写分离 → 垂直拆分 → 水平分库分表。

#### 2\. 水平拆分 vs 垂直拆分

| 类型 | 拆分方式 | 典型场景 |
| --- | --- | --- |
| 垂直分表 | 按列拆，大字段/冷字段拆到扩展表 | 主表行宽过大，TEXT 字段访问少 |
| 垂直分库 | 按业务模块拆库 | 用户库、订单库、商品库 |
| 水平分表 | 同结构按行拆到多表 | 单表数据量过大 |
| 水平分库 | 多库 + 每库多表 | 写入和存储双重瓶颈 |

```sql
垂直分表：
user(id, name, phone) + user_ext(id, avatar_blob, bio)

水平分表：
orders_0, orders_1, ... orders_15
路由：shard = user_id % 16
```

垂直拆分改动小；水平拆分需额外解决路由、全局 ID、跨分片查询和扩容迁移。

#### 3\. 全局 ID 如何设计

分库分表后不能使用单库自增 ID，需要**全局唯一、趋势递增**的主键，保证 B+Tree 插入性能。

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 雪花算法（Snowflake） | 本地生成、高性能、趋势递增 | 依赖时钟、机器 ID 分配 |
| 号段模式（Leaf） | 批量取号、DB 压力小 | 需号段服务、扩容需规划 |
| Redis INCR | 实现简单 | 依赖 Redis 高可用 |
| UUID | 绝对唯一 | 无序、占空间、索引性能差 |

```sql
雪花 ID 结构（64 bit）：
0 | 41 bit 时间戳 | 10 bit 机器 ID | 12 bit 序列号
```

生产推荐**雪花或号段**；避免 UUID v4 做主键。雪花需处理时钟回拨和多机房 workerId 分配。

#### 4\. 分页查询如何处理

分片后 `LIMIT offset, size` 需在**每个分片**执行，中间件归并排序，深分页成本极高：

```text
跨分片 ORDER BY create_time LIMIT 10000, 20 的代价：
每个分片取 10020 条 -> 中间件归并 16×10020 条 -> 排序 -> 取 20 条
```

| 方案 | 说明 |
| --- | --- |
| 游标分页 | `WHERE id > last_id LIMIT n`，避免大 offset |
| 禁止全局深分页 | 产品上限「只能翻到第 N 页」 |
| 异构索引表 | ES / ClickHouse 存排序字段，查 id 再回表 |
| 分片内分页 | 按 user\_id 分片时，用户只看自己的数据，无需跨片 |

设计分片键时尽量让高频查询落在**单分片内**，从架构上避免全局排序分页。

## 数据库连接池的核心参数有哪些？ {#connection-pool}

### 面试快答

连接池复用数据库连接并限制并发，关键参数包括最大连接数、等待超时、连接寿命和空闲策略。连接池容量要和实例数、数据库承载能力一起预算。

### 详细解析

池满可能是慢 SQL、锁等待、连接泄漏或突发流量，先看活跃数、等待数和持有时间。盲目扩池可能让数据库更慢，应结合限流与缩短事务处理。

| 参数 | 含义 |
| --- | --- |
| maximumPoolSize | **最大连接数**，过大占满 DB max\_connections |
| minimumIdle | **最小空闲连接** |
| connectionTimeout | **等待连接超时时间** |
| idleTimeout | **空闲连接回收时间** |
| maxLifetime | 连接最大存活时间，应小于 DB wait\_timeout |
| validationTimeout | 连接有效性检测超时 |

```text
经验公式（仅供参考）：
连接数 ≈ ((核心数 × 2) + 有效磁盘数)
实际需压测；过多连接反而因上下文切换降低吞吐
```

连接池耗尽表现为获取连接超时。

排查：慢 SQL 占满连接、连接泄漏（未 close）、池大小配置过小、DB 端连接数上限。

## MySQL 死锁如何排查？ {#deadlock-troubleshoot}

### 面试快答

先获取死锁日志或锁等待信息，重建各事务的访问顺序与锁范围，再统一加锁顺序、补索引或缩短事务。死锁是数据库为打破等待环主动选择事务回滚。

### 详细解析

应用可对选定的死锁失败做有限退避重试，但必须重试整个业务事务并保证幂等。不要把所有锁超时都称为死锁。

#### 排查步骤

1.  查看最近一次**死锁信息**：`SHOW ENGINE INNODB STATUS\G` 中 LATEST DETECTED DEADLOCK。
2.  分析相互等待的锁：哪两条 SQL、哪两个索引、加锁顺序是否相反。
3.  结合应用日志、TraceId 定位业务代码路径。
4.  检查**长事务**、未命中索引导致**锁范围**扩大。

```sql
-- 查看当前锁等待
SELECT * FROM information_schema.innodb_locks;
SELECT * FROM performance_schema.data_locks;  -- 8.0+
```

#### 常见原因与解决

| 原因 | 解决 |
| --- | --- |
| 加锁顺序不一致 | 统一按主键升序访问多行 |
| 大事务 | 拆小事务，尽快提交 |
| Gap Lock 冲突 | 调整隔离级别为 RC 或优化 SQL |
| 重复锁竞争 | 应用层分布式锁、重试机制 |

死锁不一定是错误，少量可接受；高频死锁需从索引、事务边界和加锁顺序上根治。

## 索引创建怎么评估？ {#index-creation-evaluation}

### 面试快答

建索引从高价值 SQL、数据分布和访问频率出发，估算选择性、覆盖收益、写入成本与空间。上线后比较计划、P95/P99、扫描量和写吞吐。

### 详细解析

先清理重复或冗余索引，在线建索引也可能消耗 I/O、日志和元数据锁。设置观测窗口和回退步骤，不以单次本地查询变快作为唯一证据。

#### 评估流程

1.  **找慢 SQL**：慢日志、APM、`performance_schema` 定位高频 / 高耗时查询。
2.  **EXPLAIN 现状**：type=ALL、key=NULL、rows 巨大 → 候选加索引。
3.  **分析 WHERE / ORDER BY / JOIN**：等值条件放联合索引前列，范围查询放后面；排序字段考虑覆盖索引。
4.  **评估选择性**：高选择性列（如 user\_id）适合索引；低选择性（性别、状态只有 2 值）单独索引收益低。
5.  **加索引后对比**：`EXPLAIN` / `EXPLAIN ANALYZE` 对比 type、rows、耗时。
6.  **观察线上**：慢查询数量、P99 延迟、写 QPS、磁盘空间、缓冲池命中率。

#### 收益 vs 成本

| 收益 | 成本 |
| --- | --- |
| 减少扫描行数，降低读延迟 | 每次 INSERT/UPDATE/DELETE 需维护索引 |
| 覆盖索引避免回表 | 占用额外磁盘与内存（缓冲池） |
| 加速 JOIN 和 ORDER BY | 过多索引让优化器选型困难、写放大 |

#### 设计原则

-   **联合索引优于多个单列**：遵循最左前缀，一个索引覆盖多种查询模式。
-   **覆盖索引**：查询列都在索引中，Extra 出现 `Using index`。
-   **避免冗余索引**：(a,b) 已存在则 (a) 通常冗余。
-   **大表在线 DDL**：用 `ALGORITHM=INPLACE, LOCK=NONE`（视版本和工具），低峰期执行，关注主从延迟。
-   **前缀索引**：长字符串（URL）可用前缀，但无法用覆盖索引完整列。

```sql
-- 加索引前
EXPLAIN SELECT id, amount FROM orders WHERE user_id=1 AND create_time > '2024-01-01';

-- 评估后创建联合索引
CREATE INDEX idx_user_time ON orders(user_id, create_time);

-- 加索引后验证：type=range, key=idx_user_time, Extra 无 filesort
```

#### 不该加索引的情况

-   小表全表扫更快（优化器可能忽略索引）。
-   写多读少且查询已够快。
-   列区分度极低且无组合条件。
-   已有索引能满足，避免「每个条件各加一个索引」。
