## Chunk 设计为什么重要？ {#chunk-design}

### 面试快答

切块决定检索单元是否语义完整、大小是否合适以及引用是否准确。应结合文档结构、问题类型、嵌入模型和上下文预算评测，避免固定长度一刀切。

### 详细解析

Overlap 能缓解边界丢失，也会增加重复结果和存储。优先按标题、段落、代码或表格切分，通过召回和最终回答质量选择参数，而不是只按 Token 数拍值。

| Chunk 大小 | 优点 | 缺点 |
| --- | --- | --- |
| 太大 | 上下文完整 | 噪声多、占 Token、语义不聚焦 |
| 太小 | 检索精准 | 语义断裂、丢失跨段关系 |

#### 最佳实践

-   按结构切：标题、段落、表格、代码块。
-   保留标题路径（breadcrumb）作为 metadata。
-   设置 10%–20% overlap，避免边界截断。
-   常见大小 256–512 Token，按文档类型 A/B 调优。

## Metadata 有什么作用？ {#metadata}

### 面试快答

Metadata 保存文档来源、租户、权限、版本、章节、时间和位置等结构化信息，用于过滤、更新、引用与审计。它是检索系统的一部分，不只是附带标签。

### 详细解析

权限过滤应在检索前或检索过程中可靠执行，不能只在生成后删句子。元数据字段需有类型和更新约束，避免源文档已撤权但索引仍可检索。

| 类型 | 示例字段 | 用途 |
| --- | --- | --- |
| 来源 | doc\_id、url、page、section | 引用溯源 |
| 权限 | tenant\_id、dept、acl | 检索前过滤 |
| 版本 | version、effective\_date | 冲突消解 |
| 技术 | embedding\_model、chunk\_rule | 重建索引 |

多租户场景下，`tenant_id` 必须在检索层强制过滤，不能仅靠 Prompt 约束。

## 向量检索的基本原理是什么？ {#vector-retrieval}

### 面试快答

向量检索把查询与候选内容映射到可比较的表示空间，按相似度返回近邻。高维索引通常用近似搜索换取速度，语义相似不等于事实正确或权限可用。

### 详细解析

离线先用精确检索作为索引召回基线，再比较近似索引损失。模型、距离函数和归一化方式要匹配，嵌入版本更换通常需要重新构建或迁移索引。

```text
文档 -> Embedding -> 向量库
查询 -> Embedding -> ANN 搜索 -> TopK 相似片段
```

#### 优势与局限

-   优势：语义相似、同义词、跨语言。
-   局限：精确编号、SKU、专有名词弱；需 Hybrid Search 补充。

## TopK 和召回率是什么？ {#topk-recall}

### 面试快答

TopK 是返回候选数量，召回率衡量相关证据被找回的比例。增大 K 可能提高召回，也会引入噪声、延迟与上下文成本，需要联合评估。

### 详细解析

区分 ANN 相对精确近邻的 recall@K 与 RAG 相对标注证据的召回，两者分母不同。多跳问题可用证据覆盖率补充，不能只用最终答案是否流畅衡量检索。

**TopK**：检索返回相似度最高的 K 个 Chunk。**召回率（Recall）**：含正确答案的文档是否被检索到。

| 参数 | K 太小 | K 太大 |
| --- | --- | --- |
| 召回 | 漏掉正确答案 | 召回率高 |
| 成本 | Rerank/生成 Token 少 | 噪声多、延迟高 |

典型策略：向量召回 K=50–100，Rerank 后取 Top5–10 进上下文。用离线评测集调 recall@K。

## Query Rewrite 解决什么问题？ {#query-rewrite}

### 面试快答

查询改写通过补全上下文、标准化术语或拆分子问题，提高查询与知识库的匹配。应保留原始问题并验证改写没有引入新假设。

### 详细解析

多路改写可合并检索并去重，但会增加成本和噪声。权限、时间和实体约束必须保留，对专有编号和精确关键词可保留原查询走稀疏检索。

#### 常见改写策略

-   指代消解：「它多少钱」→「XX 产品多少钱」。
-   关键词提取：补充领域术语。
-   问题拆分：复合问题拆成多个子查询。
-   HyDE：生成假设性答案再检索。

多轮对话需结合 `history` 或摘要后再改写，否则检索命中率低。

## RAG HyDE 是什么？ {#rag-hyde}

### 面试快答

HyDE 先生成假设性文档，再以其表示检索真实材料，可能改善短查询的语义匹配。假设文档是检索辅助，不能作为回答证据。

### 详细解析

对专业术语或少样本领域可能有收益，也可能把错误假设带入召回。与直接检索、改写及混合检索做同集对比，评估新增调用的质量和延迟成本。

```text
普通 RAG：  用户问题 → Embedding → 向量库 TopK
HyDE RAG：  用户问题 → LLM 生成假设文档 → Embedding → 向量库 TopK → 生成最终答案
```

#### 为什么需要 HyDE？

向量检索的核心是「Query 与 Document 在 Embedding 空间足够接近」。但用户问题往往是**短句、口语化**，而知识库 Chunk 是**长段落、陈述式**，两者在向量空间中分布不对称，导致直接检索命中率低。

HyDE 的思路：让 LLM 先把问题「翻译」成一段看起来像知识库文档的文字，再用这段文字去检索，缩小 Query-Doc 的语义鸿沟。

#### 流程示例

```text
用户问题：「Redis 持久化 RDB 和 AOF 怎么选？」

LLM 生成假设文档（不要求事实正确，只求风格接近知识库）：
  「Redis 提供 RDB 和 AOF 两种持久化机制。RDB 通过快照方式...
   AOF 记录每条写命令... 选择时需考虑数据安全与恢复速度...」

对假设文档 Embedding → 检索真实 Chunk → 将真实资料交给 LLM 生成最终答案
```

#### 与普通检索对比

| 对比项 | 直接 Query 检索 | HyDE |
| --- | --- | --- |
| Embedding 对象 | 用户原始问题 | LLM 生成的假设文档 |
| 语义匹配 | 短问句 vs 长文档，易失配 | 文档 vs 文档，更接近 |
| 额外成本 | 无 | 多一次 LLM 调用 + 延迟 |
| 风险 | 检索词不精准 | 假设文档可能幻觉，带偏检索方向 |

#### 适用场景

-   问题抽象、复杂，与文档表述风格差异大（如「怎么选型」「优缺点对比」）。
-   零样本 / 少样本场景，没有足够 Query 改写规则或训练数据。
-   知识库以长段落技术文档为主，Chunk 风格统一。

#### 不适用场景

-   精确匹配类查询（订单号、SKU、错误码）→ 直接用 BM25 或原 Query 更准。
-   对延迟敏感的高 QPS 接口 → 多一次 LLM 调用成本不可忽视。
-   领域知识 LLM 不熟悉 → 假设文档质量差，反而降低召回。

#### 落地建议

-   假设文档**不需要事实正确**，Prompt 中强调「风格像知识库段落即可」。
-   可与 Hybrid Search 组合：HyDE 向量召回 + BM25 关键词召回，再 Rerank 融合。
-   对假设文档做缓存（相同/相似问题复用），降低重复 LLM 开销。

## Rerank 是什么？ {#rerank}

### 面试快答

重排对初步召回的候选做更精细的相关性评分，提高送入模型的证据质量。它只能重排已有候选，无法找回第一阶段完全漏掉的资料。

### 详细解析

候选数、输入截断、批处理和模型成本共同决定延迟。先排查召回覆盖，再调重排；还要去重和控制同一文档占比，防止前几名全部是重复段落。

```text
Bi-Encoder 召回 Top100 -> Cross-Encoder Rerank -> Top5 进 Prompt
```

| 阶段 | 模型 | 特点 |
| --- | --- | --- |
| 召回 | Bi-Encoder | 快，可离线建索引 |
| 重排 | Cross-Encoder | 准，需在线逐对计算 |

只对 TopN（50–100）重排，平衡精度与延迟。

## Embedding 模型如何选型？ {#embedding-selection}

### 面试快答

Embedding 选型应在自己的语料与问题上比较检索质量，并考虑语言、领域、长度、成本和部署方式。公开榜单适合作参考，不能代替业务测试。

### 详细解析

明确查询与文档是否需要不同前缀、归一化和截断规则。升级模型时保留版本标识，混用不同嵌入空间通常不可比，需双写或重建索引并灰度验证。

#### 选型维度

| 维度 | 说明 |
| --- | --- |
| 语言 | 中文场景选 bge-m3、text-embedding-v3 等 |
| 维度 | 向量维度越高，通常表达能力更强，但成本也更高。 |
| 最大长度 | 不同模型支持的文本长度不同 |
| 检索效果 | 召回率 正确答案排序靠前等 |

用 MTEB/C-MTEB 榜单 + 自有评测集 recall@K 做最终决策；切换模型需全量重建索引。

## 向量维度对检索效果和成本有什么影响？ {#vector-dimensions}

### 面试快答

向量维度影响表示能力、存储、内存与距离计算成本，但维度越高不一定业务效果越好。应按模型支持的维度和相同评测集比较质量与成本。

### 详细解析

维度缩减不能随意截断，需使用模型支持方式或明确训练的变换。估算时还要加上索引结构、元数据、副本与运维预留，不只计算原始浮点字节。

| 维度 | 效果 | 成本 |
| --- | --- | --- |
| 低维（256–384） | 语义表达弱 | 存储小、检索快 |
| 中维（768–1024） | 平衡较好 | 主流选择 |
| 高维（1536+） | 细粒度语义好 | 内存/延迟增加 |

维度由 Embedding 模型决定，不可随意更改。百万级文档下，1536 维 vs 768 维存储差约 2 倍。

## 余弦相似度、欧氏距离、点积有什么区别？ {#similarity-metrics}

### 面试快答

余弦关注方向，点积同时受方向与模长影响，欧氏距离衡量空间距离。向量单位归一化后，几种度量的排序可能等价；未归一化时不能随意互换。

### 详细解析

选择以模型训练目标和数据库实现为准，核对返回的是距离还是相似度。不同模型或指标的分数尺度不同，阈值必须用标注集校准。

| 度量 | 公式特点 | 适用 |
| --- | --- | --- |
| 余弦相似度 | 只看方向，不看模长 | 文本 Embedding 最常用 |
| 欧氏距离 | 看绝对距离 | 未归一化向量 |
| 点积 | 方向 + 模长 | 归一化后等价余弦 |

大多数 Embedding 模型输出已 L2 归一化，余弦与点积排序一致。选型时与向量库默认度量对齐。

## 向量检索和 BM25 区别是什么？ {#vector-vs-bm25}

### 面试快答

向量检索擅长语义匹配，BM25 通过词项频率和文档长度等信号做稀疏相关性排序。专有名词、编号与精确约束常适合稀疏检索，两者可以互补。

### 详细解析

中文分词、停用词和字段权重直接影响 BM25，向量也会因领域或数字匹配失准。不要把 BM25 简化成字符串包含，评测要覆盖同义表达与精确标识。

#### 核心对比

| 对比项 | BM25 | 向量召回 |
| --- | --- | --- |
| 本质 | 关键词 / 词项匹配 | 语义相似度匹配 |
| 擅长 | 精确词、型号、错误码、字段名 | 同义表达、自然语言语义 |
| 不擅长 | 同义词、改写表达 | 数字、编号、精确匹配 |
| 例子 | E01、A100、v1.2.3 | 「无法启动」≈「开机失败」 |

#### 工作原理简述

```text
BM25：Query 分词 → 倒排索引查词频/逆文档频率 → 算 BM25 分数 → TopK
向量：Query Embedding → ANN 近邻搜索（余弦/点积）→ TopK
```

## Hybrid Search 混合检索是什么？为什么要结合向量检索和 BM25？ {#hybrid-search}

### 面试快答

混合检索并行使用稀疏与向量召回，再用融合和重排组合结果，以兼顾精确词项与语义。融合前要处理去重、权限与版本。

### 详细解析

分数尺度不同，直接相加可能失真，可评估 RRF 或经标定的权重融合。通过查询类别比较增益，避免让新增检索链路只增加延迟。

| 检索方式 | 擅长 | 弱项 |
| --- | --- | --- |
| 向量（Dense） | 语义相似、同义词 | 精确编号、SKU |
| BM25（Sparse） | 精确关键词、专有名词 | 语义理解弱 |

#### 融合方式

-   **RRF（Reciprocal Rank Fusion）**：按排名倒数加权融合，不依赖分数尺度，最常用。
-   **加权分数**：向量分 × α + BM25 分 × (1-α)，需归一化。
-   融合后通常再经 Cross-Encoder Rerank 精排 TopN 进 LLM 上下文。

## RAG 中如何处理表格、图片、PDF 复杂版面？ {#pdf-table-rag}

### 面试快答

复杂 PDF 先做版面分析、OCR 和结构恢复，再按段落、表格和图片建立可溯源单元。表格查询常需结构化解析，图片需要视觉表示或描述，并保留页码与区域。

### 详细解析

图片与文字可否共用向量索引取决于是否处于可比较的表示空间，相同维度不代表语义可比。表格跨页、单位、合并单元格和图文关联要进入质量检查。

| 类型 | 处理方式 |
| --- | --- |
| PDF 复杂版面 | Unstructured、MinerU、LayoutLM 做版面分析 |
| 表格 | 转 Markdown/HTML 或按行切片，保留表头 metadata |
| 图片 | OCR + 多模态 Embedding 或 VLM 描述后入库 |

表格切忌纯文本乱序提取；保留行列结构才能正确回答「第 3 行销售额」类问题。

## RAG 如何做增量更新？ {#incremental-update}

### 面试快答

增量更新通过稳定文档 ID、内容版本与变更事件更新索引，支持删除、撤权和失败重试。要保证新旧版本可区分，并让切换过程可恢复。

### 详细解析

先写新版本再原子切换可见标记，或通过索引别名切换，避免更新中短暂混读。保留幂等事件 ID、失败队列与对账任务，删除不能只从源系统移除。

#### 增量策略

1.  文档变更检测：Webhook / 定时扫描 diff。
2.  按 doc\_id 删除旧 Chunk（软删除标记 `is_deleted=true`）。
3.  重新解析、切片、Embedding 新内容。
4.  写入向量库，更新 metadata 版本号。

避免全量重建；Embedding 模型变更时才需全量 re-index。用消息队列异步处理，保证最终一致。

## RAG 如何设计引用和溯源？ {#citations}

### 面试快答

引用应绑定实际检索证据的文档、版本和位置，让用户能验证关键结论。生成阶段只允许引用已提供的证据 ID，展示前校验引用存在及访问权限。

### 详细解析

引用存在不等于引用支持结论，需检查段落与主张对应关系。对来源冲突要说明版本与时间，不应由模型自行选择一个未经解释的答案。

#### 设计要点

-   每个 Chunk 带 `doc_id`、`page`、`section`、`url`。
-   生成时要求标注 `[1][2]` 引用编号，映射到来源列表。
-   前端展示可点击跳转原文。

```python
上下文格式:
[1] 来源: 员工手册 v3.2 第5页
内容: 年假天数为...

回答: 根据规定，年假为15天 [1]。
```

日志记录每次检索命中和最终引用，支持审计回放。

## RAG 检索召回不准如何排查？ {#recall-troubleshooting}

### 面试快答

召回不准按解析质量、切块、权限过滤、查询表达、嵌入、索引和重排逐层定位。用标注问题追踪目标证据在哪一步消失，而不是直接增大 K。

### 详细解析

分别测精确向量、近似向量、BM25 和融合结果，区分模型问题与索引参数问题。建立失败样例集，修复后同时检查效果、延迟和成本回归。

#### 排查顺序

1.  确认问题：是检索没命中还是生成没用好？
2.  查 Embedding：模型是否与索引一致？
3.  查 Chunk：切片是否截断关键信息？
4.  查 Query：是否需要 Rewrite？
5.  查 TopK / 过滤：K 太小？权限误过滤？
6.  查 Hybrid：是否缺 BM25 补关键词？
7.  加 Rerank 对比前后 recall@K。

用离线评测集定位：retrieve 准但 answer 差 → 生成/Prompt 问题；retrieve 就不准 → 索引/切片问题。

## RAG 中 Chunk 父子块关联方案怎么设计？ {#chunk-parent-child}

### 面试快答

父子块检索用较小子块提升匹配精度，命中后取适量父级内容补足语义。设计关键是稳定关联、上下文扩展边界、去重和预算。

### 详细解析

父块过大容易重新引入噪声，多个子块命中同父块需合并。父子版本必须一致，权限与删除标记也要同步，不能绕过子块过滤返回无权父级全文。

```text
离线：文档 → 切父块（800–1500 Token）→ 再切子块（128–256 Token）
      子块 Embedding 入向量库，metadata 存 parent_id / child_index / doc_id
在线：Query → 检索 TopK 子块 → 按 parent_id 去重 → 取对应父块进 Prompt
```

#### 为什么要父子分离？

-   单一大块：Embedding 语义被稀释，TopK 命中率低。
-   单一小块：召回精准但缺前后文，LLM 容易断章取义。
-   父子关联：检索用「针」，生成用「线」，兼顾精度与完整性。

#### 数据模型设计

| 层级 | 典型大小 | 是否 Embedding | 关键 metadata |
| --- | --- | --- | --- |
| 父块 Parent | 800–1500 Token | 可选（二次召回） | parent\_id, doc\_id, section\_path, version |
| 子块 Child | 128–256 Token | 是（主检索单元） | parent\_id, child\_index, doc\_id, char\_offset |

#### 在线检索流程

1.  向量检索 TopK 子块（如 K=20）。
2.  按 `parent_id` 去重，保留每个父块最高分子块。
3.  从文档存储 / KV / 关系库加载父块原文（向量库只存子块向量 + metadata）。
4.  可选 Rerank：对「Query + 父块摘要」精排，取 Top3–5 父块进 Prompt。
5.  生成时引用子块命中位置，溯源到父块 doc\_id + section。

#### 常见实现模式

-   **双索引**：子块向量库 + 父块对象存储（S3/MinIO/ES），通过 parent\_id 关联。
-   **单索引 + 冗余**：子块 metadata 内嵌父块全文（适合父块不大、QPS 低的场景）。
-   **多级块**：Document → Section → Paragraph 三层，复杂手册/法规常用。
-   **LangChain ParentDocumentRetriever**：框架内置 child\_splitter + parent\_splitter + docstore 模式。

#### 落地注意点

-   父块更新时必须**级联重建**其下所有子块向量，按 doc\_id 批量软删再写入。
-   同一父块多个子块命中时，合并为一条上下文，避免 Token 浪费。
-   表格/代码块尽量**不切进子块中间**，按结构边界切，父块保留完整结构。
-   评测时分别看 child recall@K 和 parent 级 answer 质量，定位瓶颈在检索还是上下文组装。

## 向量数据库选型看哪些指标？ {#vector-db-selection}

### 面试快答

向量数据库选型关注实际检索质量、过滤、增量写入、删除、扩展、可用性和运维成本。Milvus、Chroma 等产品应按目标版本、部署模式与业务负载验证。

### 详细解析

不要用单机开发体验推断生产高可用，也不要把产品名直接等同于某一种复制能力。测试包含过滤后召回、并发读写、故障恢复、备份和升级，不只跑无过滤 TopK。

| 指标 | 说明 |
| --- | --- |
| 规模 | 百万 vs 亿级向量 |
| 延迟 | P99 查询 ms 级要求 |
| Hybrid | 是否原生支持 BM25 + 向量 |
| 过滤 | metadata 过滤性能 |
| 运维 | 自托管 vs 云服务、K8s 支持 |
| 成本 | 内存、存储、API 费用 |

常见：Milvus、Qdrant、Weaviate、pgvector、Elasticsearch kNN。小规模 pgvector 够用；大规模专用向量库。

## HNSW 和 IVF 有什么区别？ {#hnsw-vs-ivf}

### 面试快答

HNSW 用分层近邻图搜索，常见取舍是较高内存与较好查询效果；IVF 先聚类再搜索部分倒排单元，效果依赖训练与探测范围。选型要看数据规模和更新方式。

### 详细解析

调 HNSW 的构建与搜索参数或 IVF 的聚类与 nprobe 时，应绘制召回、延迟和内存的权衡。数据分布变化后重新测，不能只沿用初始化数据的最佳参数。

| 索引 | 原理 | 特点 |
| --- | --- | --- |
| HNSW | 分层导航小世界图 | 召回高、查询快；内存占用大 |
| IVF | 聚类分桶，搜候选桶 | 适合大规模；依赖 nprobe 调参 |

百万级以下 HNSW 常用；亿级可 IVF+PQ 压缩。无绝对最优，需 benchmark recall-latency 曲线。
