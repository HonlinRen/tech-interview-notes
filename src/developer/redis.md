## Redis 为什么快？ {#redis-fast}

### 面试快答

Redis 常见低延迟来自内存访问、高效数据结构与较少的命令执行线程竞争。它仍受网络、命令复杂度、大键、持久化和 CPU 影响，单线程不等于所有工作都只有一个线程。

### 详细解析

高版本可在部分 I/O 或后台任务中使用多线程，具体看部署配置。定位慢请求同时看客户端连接等待、网络 RTT、服务端慢日志和命令复杂度。

#### 主要原因

数据常驻内存、高效类型实现、事件驱动的网络模型和命令执行路径较少的线程协调，共同降低常见操作延迟。后台释放、复制、持久化及可选 I/O 线程并不都在同一条执行线程上完成。

#### 会变慢的情况

命令复杂度高、大键操作、热点集中、慢脚本、客户端缓冲、网络抖动和持久化开销都可能影响延迟。AOF 写入与刷盘策略、fork 和写时复制也会造成运行开销，不能说持久化绝不阻塞主路径。

#### 验证方式

按实际 key 大小、命令比例、网络和持久化配置压测，记录吞吐与 P99；单机简单 GET/SET 的宣传数字不能直接推导业务容量。

## Redis 持久化 RDB 和 AOF 区别？ {#rdb-aof}

### 面试快答

RDB 保存时间点快照，适合备份与快速加载；AOF 记录写入变更，耐久性受刷盘策略影响。可组合使用，选型依据恢复时间、可接受丢失窗口和运行开销。

### 详细解析

AOF 重写和 RDB fork 可能带来内存写时复制与延迟波动。磁盘满、备份损坏和错误写入都需要独立演练，不能把持久化等同于灾难恢复。

#### 两种持久化

RDB 保存时间点快照，丢失窗口通常覆盖最后快照后未进入可恢复记录的修改。AOF 记录写入操作，恢复与刷盘、日志结构和重写方式有关，现代版本也可能使用混合格式。

appendfsync always 通常在回复前要求相应持久化步骤，everysec 通常按秒安排 fsync，但操作系统、存储和故障会影响实际丢失窗口。不能简单写成“always 最多丢一条”或“everysec 绝不超过一秒”。

#### 成本与恢复

快照与日志重写可能涉及 fork、写时复制、额外磁盘和内存开销，放大程度取决于写入速率，不能一律说内存翻倍。使用目标版本验证恢复耗时、备份完整性与故障下的数据窗口。

副本、持久化和备份承担不同职责：逻辑误删会复制，也可能进入日志，因此仍需独立备份与恢复演练。

## 缓存穿透、击穿、雪崩是什么？ {#cache-problems}

### 面试快答

穿透是请求不存在的数据，击穿是热点缓存失效后并发回源，雪崩是大量缓存同时失效或服务不可用。分别通过校验与负缓存、重建合并、过期打散和保护下游治理。

### 详细解析

布隆过滤器有误判且需要更新机制，逻辑过期会返回旧值，互斥重建要控制锁超时。对于缓存与数据库一致性，应明确允许的陈旧窗口和失效补偿。

#### 分别治理

| 现象 | 处理思路 | 注意点 |
| --- | --- | --- |
| 不存在的数据持续回源 | 校验、短期负缓存、布隆过滤器 | 误判、更新滞后与负缓存容量 |
| 热点过期并发重建 | 同进程请求合并、受控互斥或逻辑过期 | 允许的旧值窗口、等待上限与失败回退 |
| 批量失效或缓存故障 | TTL 打散、分层缓存、限流熔断 | 下游容量和整体恢复过程 |

#### 重建与一致性

分布式重建锁也必须带持有者标识和租约，释放时校验标识，不能直接 DEL 任意过期后可能被别人持有的锁。重建失败时限制等待与重试，防止把缓存故障转成数据库雪崩。

数据库更新后通常采用失效缓存等策略，并为丢失失效事件设置 TTL、可靠通知或对账。选择依赖业务允许的陈旧窗口，不能把延时双删描述为严格一致性证明。

## Redis 分布式锁怎么实现？ {#distributed-lock}

### 面试快答

基础 Redis 锁可用带唯一值和过期时间的 SET NX PX 获取，释放时用原子脚本校验持有者再删除。租约过期与故障切换可能破坏互斥，关键写入仍需最终约束。

### 详细解析

业务执行超过租约时，旧持有者可能继续写；续期不能彻底消除暂停和分区风险。资金、库存等场景应考虑数据库条件更新、唯一约束或下游校验 fencing token。

#### 基础协议

用单条 SET key token NX PX lease 设置唯一持有者与租约。释放用脚本比较 token 后删除，防止旧持有者误删新锁；token 应来自可靠随机源并对应每次获取。

#### 故障边界

客户端暂停、网络延迟和业务超时都可能导致租约先失效而旧执行者继续操作。看门狗改善常见长任务，但不能彻底排除暂停或分区。主从异步复制还可能在切换后丢失锁记录。

不要把 Redisson、Redlock 或“用了 Lua”直接当成严格互斥的充分条件。强约束业务可在最终存储使用唯一约束、版本更新或 fencing token 拒绝过期持有者；协调服务本身也需要定义租约语义。

#### 选择依据

对可接受重复的缓存重建与对资金库存的最终写入采用不同方案，验证租约到期、切换、重复释放和调用超时后的结果。

#### 参考资料

[Redis 分布式锁的安全边界](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)（2026-10-18 核验，注意目标部署版本。）

## Redis 主从、哨兵、集群区别？ {#replication-modes}

### 面试快答

主从用于复制，Sentinel 负责监测和主从切换，Cluster 通过哈希槽分片并提供分片级故障转移。选择取决于数据规模、可用性、扩展需求和客户端能力。

### 详细解析

Cluster 有 16384 个槽，跨槽多键操作受约束，可用 hash tag 控制共槽，但要防热点。异步复制存在确认写入丢失窗口，自动切换不等于强一致。

#### 模式职责

主从复制把主节点数据复制到副本；Sentinel 监测并协调主从故障转移；Cluster 用 16384 个槽划分数据并提供分片级复制与切换。是否需要 Cluster 主要看数据与吞吐扩展需求，而非只因为要高可用。

#### 集群约束

同槽多键命令可用 hash tag 组织，但大量同标签 key 可能集中成热点。Cluster 常见生产配置为三个主节点各配副本，这不是所有实验拓扑必须达到的固定六节点下限。

客户端需要理解相应拓扑与重定向，代理方案也要确认协议兼容能力。副本读可能滞后，异步复制下故障切换存在确认写入丢失窗口。

#### 验证

检查故障转移时间、客户端恢复、跨槽业务和备份恢复，不能用“有副本”替代耐久性和一致性分析。

## Redis 内存淘汰策略有哪些？ {#eviction-policy}

### 面试快答

maxmemory 触发内存压力下的淘汰策略，allkeys 与 volatile 决定候选范围，LRU/LFU 等决定近似选择方式。过期删除与内存淘汰是不同机制。

### 详细解析

noeviction 通常拒绝需要新增内存的写命令；volatile 策略没有可淘汰过期键时也可能失败。预算还要留出复制缓冲区、碎片和 fork 额外内存。

#### 八种策略

| 策略 | 淘汰范围 | 算法 |
| --- | --- | --- |
| `noeviction` | 不淘汰 | 写命令报错，默认策略 |
| `allkeys-lru` | 所有 key | 最近最少使用（推荐缓存） |
| `allkeys-lfu` | 所有 key | 最不经常使用（Redis 4.0+，热点更准） |
| `allkeys-random` | 所有 key | 随机淘汰 |
| `volatile-lru` | 设了 TTL 的 key | LRU |
| `volatile-lfu` | 设了 TTL 的 key | LFU |
| `volatile-random` | 设了 TTL 的 key | 随机 |
| `volatile-ttl` | 设了 TTL 的 key | 优先淘汰 TTL 更短的 |

#### LRU vs LFU

-   **LRU**：淘汰最久未访问的 key，适合访问模式较均匀的场景。
-   **LFU**：淘汰访问频率最低的 key，适合有明显热点、长尾 key 多的场景。
-   Redis 的 LRU/LFU 是**近似算法**（采样而非精确），节省内存与 CPU。

## Redis 内存异常增长如何排查？ {#memory-growth}

### 面试快答

先检查 key 数量、平均大小、类型分布、过期设置和碎片，再区分业务增长与客户端缓冲区等额外开销。用渐进扫描采样，避免线上 KEYS 或直接遍历大键。

### 详细解析

对比 used_memory、RSS 和碎片指标，并关联发布与流量。治理前确认数据所有权及 TTL，不能在没找到增长来源时批量删键。

#### 排查步骤

1.  `INFO memory`：看 used\_memory 趋势、mem\_fragmentation\_ratio、maxmemory 使用率。
2.  `INFO clients`：客户端输出缓冲区是否过大（慢消费者堆积）。
3.  找大 key：`redis-cli --bigkeys`，或 RDB 分析工具（rdb-tools、redis-memory-analyzer）。
4.  `SCAN` + `MEMORY USAGE key` 抽样检查异常 key 类型与大小。
5.  检查 List/Set/ZSet/Stream 是否只增不删；缓存 key 是否未设 TTL。
6.  核对 AOF rewrite、主从复制 backlog 是否占用过多缓冲。

```redis
INFO memory
MEMORY USAGE mykey
redis-cli --bigkeys -i 0.1

# 碎片率过高时可尝试（Redis 4.0+，会短暂阻塞）
MEMORY PURGE
# 或重启 / 开启 activedefrag
```

#### 常见原因

| 原因 | 处理 |
| --- | --- |
| 大 key / 热 key 膨胀 | 拆分 key、压缩 value、设置合理 TTL |
| 无过期缓存堆积 | 统一 key 规范，强制 TTL |
| 内存碎片 | active defrag、低峰重启、控制大 key 频繁更新 |
| 持久化/复制缓冲 | 调 repl-backlog-size、避免过大 AOF |

## Redis 如何实现滑动窗口限流？ {#sliding-window-rate-limit}

### 面试快答

可用 ZSet 存储请求时间和唯一成员，原子地清理窗口外记录、计数并决定是否放行。分布式实例共享同一限流状态，但要考虑时钟、热点和存储成本。

### 详细解析

每请求一条记录在高 QPS 下开销很大，可改成桶计数或令牌桶近似。脚本要设过期且限制规模，明确 Redis 不可用时 fail-open 还是 fail-closed。

#### 基于 ZSet 的实现

以时间戳为 score，member 为请求唯一 ID；每次请求前删除窗口外记录，统计剩余数量，未超限则写入并放行。

```redis
# key = rate:{userId}:{api}
# 窗口 60 秒，上限 100 次

now = 当前毫秒时间戳
windowStart = now - 60000

ZREMRANGEBYSCORE key 0 windowStart      # 清理过期
count = ZCARD key
if count < 100:
  ZADD key now requestId
  EXPIRE key 61
  放行
else:
  拒绝
```

#### 生产注意点

| 要点 | 说明 |
| --- | --- |
| 原子性 | 清理 + 计数 + 写入 + EXPIRE 用 Lua 脚本一次完成 |
| member 唯一 | 用 UUID 或 `now:seq`，避免同毫秒冲突 |
| 内存 | 窗口内每条请求占一条 ZSet 记录，高 QPS 时注意 key 大小 |
| 替代方案 | 令牌桶/漏桶（Redisson RRateLimiter）；固定窗口用 INCR + EXPIRE 更简单 |

## 为什么用 Redis 而不是本地缓存？ {#redis-vs-local-cache}

### 面试快答

本地缓存延迟低且减少网络开销，Redis 便于多实例共享状态与统一失效。两者可组成多级缓存，代价是更复杂的一致性、容量和回源控制。

### 详细解析

本地热点会在每个实例重复占内存，Redis 故障可能同时放大所有实例回源。方案需规定 TTL、版本、失效广播和下游熔断，避免缓存层越多越难排障。

Redis 提供跨进程、跨节点的共享缓存，适合分布式系统；常配合本地缓存做多级缓存。

## Redis 事务为什么不支持回滚？ {#redis-tx-no-rollback}

### 面试快答

MULTI/EXEC 将一组命令排队后连续执行，但不提供关系型数据库式回滚。运行时某条命令失败，不代表已执行命令撤销或后续命令全部停止。

### 详细解析

WATCH 用于乐观并发检测；Lua 的原子执行也不意味着脚本报错会撤销之前的写入。操作前验证类型与参数，复杂一致性尽量收敛为明确的单步状态转换。

#### Redis 事务实际提供了什么

```redis
MULTI
SET key1 val1
INCR counter
EXEC
```

-   **批量执行**：EXEC 前命令进入队列，EXEC 时一次性顺序执行。
-   **隔离性（有限）**：EXEC 执行期间不会被其他客户端命令插入。
-   **不保证原子性回滚**：某条命令执行失败，前面已执行的命令不会撤销。

#### 为什么不支持回滚

| 原因 | 说明 |
| --- | --- |
| 设计定位 | Redis 是内存 KV，追求**极致性能**，不是通用 OLTP 数据库 |
| 实现成本 | 回滚需要 undo log、版本链，与 Redis 单线程 + 简单数据结构理念冲突 |
| 使用场景 | 多数场景是缓存/计数/锁，不需要复杂事务；开发者可用 Lua 保证逻辑原子性 |
| 错误类型简单 | Redis 命令失败多为类型错误（如对 string 做 LPUSH），属于编程错误，应在开发期发现 |

#### 两类错误的不同行为

| 错误类型 | 示例 | 行为 |
| --- | --- | --- |
| **入队错误** | 语法错、命令不存在、参数个数不对 | 整个事务**不执行**，EXEC 返回错误 |
| **运行时错误** | 对 string 执行 LPUSH、对不存在 key 做特定操作 | 出错命令失败，**其余命令照常执行，不回滚** |

```redis
MULTI
SET key "hello"
LPUSH key "world"    # 运行时错误：key 是 string 不是 list
INCR counter
EXEC
# 结果：SET 和 INCR 已生效，LPUSH 报错，不会整体回滚
```

#### 与 MySQL 事务对比

| 对比项 | MySQL（InnoDB） | Redis MULTI/EXEC |
| --- | --- | --- |
| 回滚 | 支持 ROLLBACK | 不支持 |
| 隔离级别 | RC / RR 等 | 仅 EXEC 期间不被插队 |
| 持久性 | redo log 保证 | 取决于 AOF/RDB 配置 |
| 典型用途 | 业务强一致事务 | 批量命令、简单原子操作 |

#### 需要原子性时怎么办

-   **Lua 脚本**：多条逻辑在一个脚本中原子执行，Redis 保证脚本执行期间不被打断（推荐）。
-   **WATCH + MULTI + EXEC**：乐观锁，被 watch 的 key 在 EXEC 前被改动则事务失败，需客户端重试。
-   **单条命令**：`SET NX`、`INCR`、`GETSET` 等本身原子。

```redis
-- Lua 示例：扣减库存（原子）
EVAL "
  local stock = tonumber(redis.call('GET', KEYS[1]))
  if stock >= tonumber(ARGV[1]) then
    return redis.call('DECRBY', KEYS[1], ARGV[1])
  else
    return -1
  end
" 1 product:1001 1
```

## Redis 常用数据结构及底层实现是什么？ {#data-structures}

### 面试快答

Redis 数据类型应按访问操作选：String 做值和计数，Hash 表达字段，Set 去重，ZSet 排序，List/Stream 表达不同队列需求。逻辑类型与内部编码不是一回事。

### 详细解析

内部编码随版本、大小和配置变化，ZSet 常见紧凑编码与跳表/哈希组合。队列是否需要持久化、确认和重放应先明确，不能用普通 List 自动获得可靠消息语义。

| 类型 | 典型编码 |
| --- | --- |
| String | SDS、int、embstr |
| Hash | ziplist、hashtable |
| List | quicklist |
| Set | intset、hashtable |
| ZSet | ziplist、skiplist+hashtable |

## Redis Big Key 和 Hot Key 分别是什么？ {#big-hot-key}

### 面试快答

Big Key 是单键数据量或成员过大，Hot Key 是单键访问集中，两者可能同时存在。大键重点拆分与渐进治理，热键重点复制热点、局部缓存和削峰。

### 详细解析

用采样、监控和慢日志定位，扫描要控制速率。删除大键优先评估 UNLINK 等异步释放方式，热点拆分则需处理聚合与一致性。

Big Key：value 过大或集合元素过多，导致阻塞、迁移慢。Hot Key：访问频率极高，造成单分片/单节点压力过大。

## Redis Pipeline 是什么？ {#pipeline}

### 面试快答

Pipeline 批量发送命令并批量接收响应，主要减少网络往返和系统调用。它不是事务，不自动提供跨命令原子性，也不解决命令间依赖。

### 详细解析

批次过大增加内存、响应延迟和单连接占用。根据请求大小与延迟预算限制批量，在 Cluster 客户端中确认跨节点拆分及失败重试语义。

客户端批量发送多条命令再批量读取结果，减少 RTT，但不保证事务原子性。适合大量独立读写。

## Redis Lua 脚本为什么能保证原子性？ {#lua-atomic}

### 面试快答

Redis Lua 脚本通常在执行期间不与其他命令交错，适合读改写和多步校验。原子性指执行隔离，不意味着数据库事务式回滚。

### 详细解析

脚本应短小有界，避免长循环阻塞命令处理。Cluster 中涉及的 key 一般需共槽，并通过 KEYS 显式声明，不能动态访问任意键。

常用于分布式锁释放、限流、库存扣减。脚本应短小，避免阻塞主线程。

## Redis 主从复制全量同步和增量同步是什么？ {#replication-sync}

### 面试快答

全量同步传输基础数据再追上增量，部分同步利用复制历史偏移续传。能否续传受复制标识、历史缓冲区和断连时长影响。

### 详细解析

大规模重连可能造成主库 fork、网络和磁盘压力，应按真实写入率规划 backlog。同步完成与应用可读、故障切换可接受的丢失窗口仍是不同判断。

全量同步：从库首次连接或 offset 差距过大时，主库 RDB 快照 + 缓冲期间命令。增量同步：基于 replication backlog 传播 offset 之后的写命令。

## Redis 脑裂问题是什么？如何降低风险？ {#split-brain}

### 面试快答

网络分区时旧主可能继续接收部分客户端写入，新主也可能被提升，恢复后旧主写入可能丢失。需缩小可写窗口、隔离旧主并让客户端及时发现新拓扑。

### 详细解析

min-replicas-to-write 等配置能降低部分风险，但不是严格共识保证。业务若要求线性一致，应选匹配的一致性存储或在最终写入端增加校验。

网络分区导致出现多个 master 同时写入，恢复后可能丢数据。治理：min-replicas-to-write、合理超时、Sentinel/Cluster 多数派选主。

## Redis 连接池如何管理？ {#redis-pool-management}

### 面试快答

客户端连接应通过成熟驱动复用，设置连接、读写、池等待超时与合理上限。连接、事务或 Pipeline 上下文不能被不安全地跨线程、协程共享。

### 详细解析

部分客户端支持多路复用，不一定需要传统大连接池，应以驱动语义为准。异步客户端要绑定正确事件循环，事务使用独占上下文并在取消和异常时归还资源。

**提前创建一批 Redis TCP 连接，业务线程需要访问 Redis 时，从池里借一个连接，用完再归还，避免每次都新建/释放连接** 

Redis 连接池主要是为了复用 TCP 连接，避免频繁创建和销毁连接。

应用启动后会维护一批 Redis 连接，请求访问 Redis 时从连接池借连接，执行完命令后归还连接。

连接池会通过参数控制最大连接数、空闲连接数和获取连接等待时间

如果连接池满了，新的请求会等待，超过 max-wait 就会报超时。

连接池打满需要注意：

连接泄漏、连接池配置过小、Redis 命令耗时过长，连接池大小后是否超过 Redis 服务端承载能力。
